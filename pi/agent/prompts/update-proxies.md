---
description: Безопасно обновить CLIProxyAPI и CPA Manager Plus с проверкой и откатом
---

Без дополнительного согласования проверь и, если нужно, обнови:

- https://github.com/router-for-me/CLIProxyAPI
- https://github.com/seakee/CPA-Manager-Plus

Цель: поставить последние стабильные Linux amd64-релизы, не потерять состояние и сохранить работающий откат. Текущая сессия использует CLIProxyAPI, поэтому обновляй его последним и минимизируй его простой.

1. **Инвентаризация.** До изменений установи из systemd и файловой системы:
   - архитектуру, unit-файлы, `ExecStart`, пользователей, пути бинарников и данных;
   - текущие версии или точное соответствие установленного бинарника релизу;
   - PID, активность, автозапуск, число рестартов и слушающие порты;
   - свободное место, чтобы вместить загрузки и одну полную rollback-копию каждого сервиса.

   Не запускай `cpa-manager-plus` с `--version`, `version` или без штатной конфигурации: бинарник не поддерживает безопасный version-only режим, может запустить сервер, создать новый admin key, конфигурацию и SQLite-файлы и вывести секрет в журнал. Определяй его версию без запуска: по точному сравнению с релизным бинарником, SHA-256 или однозначной version-строке из бинарника. У CLIProxyAPI вывод версии может сопровождаться кодом 2 и usage; не считай это сбоем сервиса. Не печатай API/OAuth/admin-ключи и содержимое конфигурации.

2. **Выбор релиза.** Через GitHub Releases API получи `releases/latest` обоих репозиториев и убедись, что релизы не draft и не prerelease. Сравни версии семантически. Если обе уже актуальны, ничего не перезапускай: только проверь работающие бинарники и runtime-состояние и перейди к отчёту.

3. **Подготовка без простоя.** До остановки сервисов:
   - скачай оба amd64-архива и соответствующие `checksums.txt` во временный каталог;
   - проверь SHA-256 архива по точной строке его имени из `checksums.txt`;
   - распакуй архивы, проверь наличие и исполняемость ожидаемых бинарников;
   - размести новые бинарники как временные `.new` на том же filesystem, что и конечный путь, с текущими владельцем и mode, чтобы финальная замена была атомарной;
   - подготовь закрытые каталоги rollback-копий с timestamp и manifest со старыми/новыми версиями и SHA-256.

4. **Состояние и rollback.** Перед заменой сохрани:
   - текущие бинарники, включая `cpa-manager-plusctl`;
   - конфигурацию CLIProxyAPI, OAuth/auth-файлы и локальную usage-базу;
   - конфигурацию CPA Manager Plus, admin-key file, data key и SQLite-базу вместе с WAL/SHM.

   Для согласованной копии SQLite останови только соответствующий сервис и копируй файлы после его остановки. После штатной остановки SQLite может удалить WAL/SHM: копируй их, только если они существуют, а отсутствие зафиксируй в manifest и не считай ошибкой. Не выполняй SQL-запросы к базе. Не перезаписывай и не удаляй существующие пользовательские rollback-копии.

5. **Последовательное обновление.** Не заменяй и не перезапускай компонент, для которого новая версия не найдена. Остальные обновляй строго по одному сервису:
   1. CPA Manager Plus: остановка для финального snapshot, атомарная замена основного бинарника и `cpa-manager-plusctl`, запуск, полная проверка.
   2. Только после успеха CPA Manager Plus — CLIProxyAPI: заранее скопируй неизменяемый старый бинарник, во время короткой остановки сделай финальный snapshot изменяемого состояния, атомарно замени бинарник и сразу запусти сервис. Измерь окно простоя.

   Выполняй замену как транзакцию с явными фазами `old-running`, `old-stopped`, `new-installed`, `new-running`, `verified`; при ошибке запиши фазу и точную провалившуюся проверку, не раскрывая секреты. Fail-safe не должен оставлять сервис остановленным.

   Если ошибка произошла до замены бинарников, запусти и полностью проверь старый процесс; это не откат установленной версии, и после устранения причины подготовку этого же сервиса можно повторить. Если новый бинарник уже установлен или запущен и установка либо проверка не прошла, выполни настоящий откат:
   1. останови работающий новый процесс и дождись его завершения;
   2. размести сохранённые старые бинарники как временные файлы на целевом filesystem и атомарно верни их на конечные пути;
   3. запусти сервис и проверь, что `/proc/<PID>/exe` имеет SHA-256 именно старого бинарника, а не удалённого нового executable;
   4. повтори проверки systemd, порта, авторизованного HTTP, состояния и журнала уже для старого процесса.

   Не заменяй файл старым поверх работающего нового процесса и не считай `systemctl start` откатом, пока новый PID не остановлен. После настоящего отката не повторяй установку и не продолжай обновление второго сервиса. Базу из snapshot автоматически не восстанавливай, если для этого нет доказанной необходимости; сохрани её для ручного восстановления.

6. **Проверка каждого нового процесса.** Обновление сервиса завершено только когда одновременно доказано:
   - systemd unit — `active` и `enabled`, PID ненулевой, неожиданных рестартов нет;
   - ожидаемый localhost-порт слушается (`8317` для CLIProxyAPI, `18317` для CPA Manager Plus);
   - `/proc/<PID>/exe` побайтово совпадает с проверенным релизным бинарником либо имеет тот же SHA-256;
   - CLIProxyAPI отвечает HTTP 200 на `/` и на авторизованный `/v1/models`; ключ прочитан в переменную и нигде не выведен;
   - CPA Manager Plus отвечает HTTP 200 на авторизованный `/status`; admin key прочитан из настроенного key file и не выведен; collector не сообщает сбой, присутствующий `lastError` пуст, миграция не failed, присутствующий maintenance-status не требует обслуживания БД;
   - конфигурация, ключи и OAuth-файлы сохранились; рабочие файлы баз существуют и ненулевые;
   - в журнале **текущего запуска** нет warning/error/fatal/panic.

   `active` означает, что процесс запущен, но не что приложение уже слушает порт. После запуска опрашивай порт, затем HTTP-путь до общего ограниченного дедлайна не менее 30 секунд; используй короткие интервалы и таймаут каждого запроса. Не откатывай из-за первой проверки `connection refused` или отсутствующего listener, пока процесс жив, не перезапускается и дедлайн не истёк. Заверши ожидание раньше только при терминальном признаке: unit стал `failed`/`inactive`, PID исчез, возник неожиданный рестарт либо журнал текущего запуска содержит fatal/panic. После первой успешной HTTP-проверки выжди короткое окно стабильности и повтори systemd, PID, SHA-256, порт и HTTP; только затем помечай фазу `verified`.

   Ограничивай журнал временем `ActiveEnterTimestamp` нового процесса. Используй тихий вывод `journalctl -q` или считай реальные записи: строка `-- No entries --` не является ошибкой. Не принимай ожидаемые сообщения остановки старого процесса вроде `context canceled` за ошибку нового запуска.

7. **Завершение.** Перед удалением staging проверь по SHA-256, что executable каждого работающего PID соответствует бинарнику, который должен остаться после успеха или отката. Удали только созданный этой задачей staging и лишнюю rollback-копию неудачной попытки; сохрани по одной проверенной финальной rollback-копии для каждого обновлённого сервиса. Повтори совместную проверку обоих сервисов, портов, HTTP-путей и журналов уже после всех замен или отката.

В конце кратко сообщи:

- старую и новую версии каждого компонента либо что обновление не требовалось;
- результат проверки release SHA-256;
- состояние сервисов, портов и HTTP-проверок;
- сохранность конфигурации/OAuth/БД и состояние CPA collector/maintenance;
- число ошибок в журналах, простой CLIProxyAPI и пути rollback-копий;
- выполнялся ли автоматический откат и чем завершилась повторная проверка.
